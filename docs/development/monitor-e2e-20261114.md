# 真实 Agent / Kata / eBPF 联合观测验证（2026-11-14）

## 结论

已在 117 跑通 **真实 Codex + Qwen → Session SDK → Core run/cgroup → eBPF → 事后 trace 关联 → Guest 退出后离线重读**。
这是有限观测契约下的集成验证，不是“全过程、任意行为均完整可见”。

- 成功记录：`/data/hy/Allox/monitor-e2e-20261114/attempt-a4ea595629`。
- 实际模型：已有的 `Qwen3.5-4B-CPU-Test`；2 次模型请求均 HTTP 200，Codex 实际执行 1 次 shell 工具，运行 12 个 action。
- 产生 41 个完整结束的 span，其中 Session SDK 36 个；SDK 72 个事件全部确认。
- 实际采到 4424 条系统副作用事件、265 条生命周期事件；两类事件均可按 Core 所绑定的 Agent/Session/run/trace 关联。
- 所采 hook 的 attempted/published/persisted 数量一致，报告 dropped=0；独立 verifier 为 VERIFIED。不能据此证明从未被 hook 覆盖的行为没有丢失。
- Guest 删除后再次分页读取原始证据，身份、哈希和关联结果仍一致。

## 实际环境与变更

通过指定跳板连接 117；实验根目录 `/data/hy/Allox/monitor-e2e-20261114`。
每次构建、运行重新读取 online CPU，当前最后 24 个为 `24–47`；独立 Kata 的 shim/QEMU 线程在释放 Guest 工作负载前绑定。
Guest 为 4 vCPU / 4 GiB，真实 Btrfs；未改共享宿主机内核或全局 Kata 配置。

不是原来的 6.1 Guest：它缺少所选对象解析器要求的 `file_post_open`。
本轮使用 SHA256 固定的官方 Linux 6.12.107 源码，加以下**独立测试 Guest 补丁**：

1. 增大 vsock RX 缓冲区，适配旧宿主 vhost 的大包；调整前小 RPC 成功、大 RPC 失败，调整后容器成功启动。
2. 移植[上游双参数退出 tracepoint](https://github.com/torvalds/linux/blob/v6.16/include/trace/events/sched.h)，直接传递 `do_exit` 的 `group_dead`，不靠计数器推测。
3. 为复制出的 Kata 3.10 Guest agent 修复 ttrpc 非 INET socket 的 `SO_REUSEPORT`，保留 9p。没有切换或重启共享宿主服务。
4. 挂载 Guest tracefs，补齐 syscall tracepoint 配置。

Observer 原始对象实际加载失败：accept 路径四层调用累计栈为 560 字节，超过 BPF 的 512 字节限制。
单独内联仍失败；最终通过内联和专用 per-CPU 临时缓冲修复，未跳过 hook、关闭 verifier 或删减事件。
这些修改以 [测试构建补丁](../../examples/monitor_e2e/) 保存；**不能据此宣称 stock 6.12 / 原始 Observer 二进制开箱即用**。

Allox 自身另修复一处 bug：小流索引路径已校验内容，但返回的 `provenance.stream_sha256` 错用未更新的 fallback hasher。
现在返回实际验证的摘要，并对首次索引、缓存命中、流式 fallback 补了断言；篡改拒绝仍保留。

## 覆盖与保守结论

验证了普通文件写/读后校验、rename/chmod、HTTP 请求、Unix socket bind/connect、子进程创建，以及它们的 SDK 计时和所选系统调用事件。
对其他 Agent/Session 标识、跨身份查询拒绝、原始流篡改拒绝分别做了检查。
身份用例是独立 Store 下的绑定测试，**不是共享 Store 下的并发隔离或越权攻击测试**。

单一 Core 父 turn 为 `declared_parent_turn`；同一进程 run 存在多个 SDK turn 时保持 `ambiguous`。
不能把 run 级内核事件强行归到某个具体 tool/action。

以下缺口仍存在：

- 生命周期没有权威的 S0 task/thread 清单及 cgroup 迁入/CLONE_INTO_CGROUP 登记。因此 lifecycle=`PARTIAL`、全局 evidence=`INCOMPLETE`，测试要求保留这些标签。
- `balanced` 策略不采 `read` syscall，也不覆盖 mmap 后脏页、io_uring、委托/异步因果等全部行为；读后校验不是内核级 read 覆盖。
- Unix socket 创建/连接 syscall 可见，不等于 Unix socket 内核对象状态或恢复完整；TCP 状态流另有自己的部分覆盖契约。
- Agent 工具内部由测试 SDK 显式埋点；模型经测试代理计时，不是自动发现任意框架内部阶段，也没有凭空补出 TTFT/服务端时间。
- `profile.complete` 只说明收到的 span 已结束，不代表完整内核观测。未测试本轮 rollback、断电或对抗性进程逃逸。

## 性能与回归

真实 Agent 单次总时长约 157.4 秒，其中模型 span 合计约 146.9 秒；这不是监控开销测量。
固定负载的 10 组开关对照单独记录，不调用模型。完整 run 计时包括 Observer 初始化/终结和 SDK 排空；任务内计时包括 action 循环和 SDK close。
均不包括 VM 启动、Store/DB 初始化或事后关联查询；不能将其与旧 SDK-only 微基准直接横比。

`attempt-885fe441fd` 的 20 次执行全部通过；开关顺序逐组交替，0 次模型请求。
业务均为相同的 12 个 action；监控内部 IPC 随批次调度可变化，不要求原始 syscall 总数逐次相同。

| 计时范围 | 关闭中位数 | 开启中位数 | 配对差值中位数 |
| --- | ---: | ---: | ---: |
| 完整执行生命周期 | 3386.83 ms | 7475.07 ms | +4084.04 ms |
| 任务循环 + SDK close | 1999.01 ms | 2343.31 ms | +414.84 ms |

中位数之差不等于配对差值的中位数。完整耗时中位数约增 120.7%，任务内约增 17.2%；不是零开销。

这里没有把这些组成部分单独计时，不能据此精确归因给某一个函数，更不能把全工具链结果当作纯 eBPF 开销。
共享宿主磁盘、缓存、其他负载未完全控制；10 个样本不构成尾延迟保证。

## 11 月 15 日：生命周期额外 4 秒的定位

本轮只做诊断，未修改生产路径、减少 hook、关闭同步或放宽验证。
继续在 117 同一独立 Kata/Guest/Btrfs 环境运行，CPU 每次重新选择最后 24 核。
10 组交替 off/batch 的同负载复测全部通过；另做 3 组 native syscall 计时、3 组内核栈采样，均通过原有证据和关联检查。

为避免分阶段中位数无法相加，下表使用 **10 次均值**，单位 ms：

| 阶段 | 关闭 | 开启 | 新增 |
| --- | ---: | ---: | ---: |
| Core start 前的框架事件 | 0.13 | 97.15 | 97.02 |
| 进程准备、Observer READY、放行 | 716.88 | 1381.28 | 664.40 |
| 放行后至 root 退出 | 2524.18 | 2865.33 | 341.15 |
| root 退出至终结完成 | 93.33 | 2928.64 | 2835.30 |
| **合计** | **3334.52** | **7272.40** | **3937.87** |

约 3.60 秒在启动/结束路径，约 0.34 秒在执行期间。与上一批约 4 秒的结论一致，批次波动不代表优化效果。
启动 gate 的约 0.7 秒是开关两边共有成本，不应全算作监控新增。

### 主要瓶颈：每 run 销毁 BPF links，反复等待内核安全撤销

未启用 strace 的 10 次阶段计时中位数：

- Observer 初始化约 **391 ms**，其中等待 READY 约 339 ms。
- Observer `finish` 约 **2677 ms**，其中等待 FINISHED 约 **2348 ms**。
- 独立 verifier 约 **220 ms**；收到 FINISHED 后等待子进程退出仅约 3 ms。
- cgroup freeze/thaw、空组确认和移除均为毫秒级。

对 3 次 Observer 的原生系统调用采样，FINISH 区间每次均关闭 **25 个 BPF_LINK_CREATE 返回的 link fd**。
对应 `close()` 累计分别 **1727、1726、1735 ms**，部分单次约 100 ms；同一主线程顺序执行。
Observer 源码 `crates/system-effects-recorder/src/lib.rs` 的 `KernelResources::drop` 对 link 逐个执行 `bpf_link__destroy`，每次执行都重建/销毁这批资源。

另一组不启用 strace、只在 FINISH 时每约 5ms 读取自有 Observer 内核栈的实验，重复捕获：

```text
close → bpf_link_release → bpf_tracing_link_release
      → bpf_trampoline_unlink_prog → unregister_ftrace_direct
      → ftrace_shutdown → synchronize_rcu_tasks_rude → __wait_rcu_gp
```

因此已定位到 **逐个撤销探针时的 RCU/ftrace 同步等待**，不只是“Python 在等子进程”。
该内核 RCU tasks-rude 源码含 `HZ/10` 的轮间休眠，与部分 close 接近 100ms 相符；这不是每次必定睡 100ms 的保证，也不是修改 RCU 参数的安全性证明。本轮未修改它。

### 次要成本：证据同步与 verifier

原生采样中 FINISH 区间每次约 14 次 fsync，合计 **323–425 ms**。
独立内核栈采样也观察到 `p9_client_fsync → v9fs_file_fsync_dotl`，说明此实验的证据目录经 Guest 9p 同步到宿主机，确实有等待。
Observer 自带 closing-drain 计时约 0.24 秒，包含部分输出同步；它与 fsync 数字重叠，**不能再相加**。
未启用 strace 的 verifier 中位数约 220ms，Python 写回执、运行状态和框架事件还有额外持久化成本。

strace 明显扰动耗时：其 Observer 初始化中位数约 2.34 秒、等待 FINISHED 约 3.01 秒，均高于非 strace 结果。
因此正式阶段开销取 10 组普通计时；strace 只定位具体调用，再用非 strace 的内核栈交叉验证，不能把它的总耗时冒充真实基准。

后续优先评估 Observer/探针长驻复用，按 run 做注册、隔离、排空和证据封存，以摊销重复销毁成本；TCP 异步 producer 的封闭证明需要保留，不能简单删掉 detach。
其次优化证据提交与重复同步，在保留耐久性保证的前提下减少同步轮次。本轮没有实施这些改动。
